# Лабораторная сторона провайдера

## Схема

Основной Asterisk принимает SIP на UDP 5060; SIPp будет использовать 127.0.0.1:5062. Транк lab-provider имеет статический AoR contact=sip:127.0.0.1:5062. identify_by=ip исключает идентификацию этого endpoint по имени пользователя, identify match ограничивает источник IP и портом локального SIPp. Пароль и SIP REGISTER для этого лабораторного транка не используются. IP identifier ранее подтверждён Running на VPS.

qualify_frequency=0 отключает автоматические OPTIONS этому тестовому узлу. Наличие статического контакта само по себе не доказывает, что SIPp запущен; связь проверяется реальным вызовом. timers=no отключает session timers на тестовом endpoint. direct_media=no оставляет медиа через Asterisk.

Для исходящего из АТС вызова SIPp будет запущен как UAS и ответит на INVITE. Для входящего в АТС — как UAC, передающий DID и тестовые SIP-заголовки. Два процесса не должны одновременно занимать 5062; сценарии будут запускаться последовательно. Перед запуском ss подтвердил отсутствие слушающих UDP-сокетов 5062 и 6000.

## Принятая трактовка входящих маршрутов

- 74990000000–74990000009: IVR, тот же контекст, что у внутреннего 2000. Набор 3XXX вызывает сотрудника, ожидание ведёт в очередь cc.
- 74990000010: напрямую tp-entry со случайным выбором зарегистрированного ТП из AstDB.

Специальное требование про ТП трактуется как исключение из общего правила про вход в IVR. Эта трактовка принята самостоятельно, без уточнения у HR, и должна быть озвучена на защите. В from-provider нет include from-internal; другие DID и прямой доступ к внутренним номерам/исходящим маршрутам не добавлены.

## Исходящие сотрудники

Контекст from-internal сохраняет точные сервисные 2000/2001 и более специфичный шаблон _3XXX. Остальные номера попадают в to-provider; ведущий + удаляется. Затем допускаются только цифры длиной 2–15; иная строка завершается с причиной 28. Восьмёрка на семёрку не заменяется: нормализация под реального провайдера не задана.

Dial(PJSIP/${OUT_NUMBER}@lab-provider,30) подставляет набранный номер в user part SIP URI и использует адрес статического AoR. Это ожидание ответа до 30 секунд, не предел длительности разговора. В IVR исходящие шаблоны отсутствуют: неверный добавочный обрабатывается как ошибка IVR.

## Применение конфигурации

Файлы config/pjsip.conf, config/pjsip-provider-lab.conf и config/extensions.conf входят в итоговый комплект. После их применения проверить endpoint/identify и контексты, затем реальные вызовы. Порядок установки полного стенда описан в setup.md.

## Проверки и пределы

Проверены все11DID, исходящий транк, внутренний маршрут после общего шаблона, передача и изоляция заголовков двух Queue-вызовов. Неизвестный DID отдельно не тестировался. SIPp UAC/UAS уже проверены для исходящего номера и DID ТП. Перенос первых значений X-* применён и проверен на двух полях в INVITE оператора Queue.

Это имитация SIP-стороны провайдера. Она не подтверждает выход в реальную городскую телефонную сеть; для него необходим действующий провайдер и его параметры.

## Одиночный исходящий вызов с RTP-эхо

Команда подготовлена в scripts/run_provider_uas.sh. В PuTTY запускается встроенный сценарий SIPp uas на SIP 127.0.0.1:5062 и RTP 127.0.0.1:6000 с -rtp_echo. Затем с Zoiper 3000 вызывается внешний тестовый номер 74991234567. SIPp отвечает, а полученный RTP отправляет обратно отправителю: пользователь должен слышать своё эхо. Завершить вызов на 3000; -m 1 завершает SIPp после одного обработанного вызова. Проверить итоговые Successful call/Failed call и исходный INVITE в журнале.

SIP-трасса сохраняется в /var/log/asterisk/sipp-outbound-messages.log, ошибки — sipp-outbound-errors.log. При повторном запуске эти файлы по умолчанию перезаписываются. Сырые трассы остаются вне Git; для проекта сохранить только необходимые строки без секретов. Запуск и один успешный вызов подтверждены итоговым экраном SIPp; номер в INVITE и слышимость эха затем подтверждены.

Для повторения команды через файл его нужно отдельно передать на VPS; текущая инструкция пользователю содержит саму команду и не предполагает, что scripts/ уже перенесена целиком.

Читать: [SIPp UAS](https://sipp.readthedocs.io/en/latest/int_scenarios.html#uas) и [RTP echo](https://sipp.readthedocs.io/en/latest/media.html#rtp-echo).
## Одиночный входящий UAC-вызов

Подготовлен sipp/provider-uac.xml, на VPS его разместить как /etc/asterisk/sipp/provider-uac.xml. Wrapper сохранён в scripts/run_provider_uac.sh; инструкция первого запуска содержит полную команду и не требует переноса wrapper на сервер.

SIPp подключается с 127.0.0.1:5062 к 127.0.0.1:5060; DID подставляется параметром -s. Предлагает PCMU и telephone-event, принимает ответ и отправляет ACK на Contact АТС. Затем ждёт BYE до 90 секунд и отвечает 200. Вызов следует завершить на телефоне сотрудника. Короткая пауза в конце оставляет время для обработки завершающих сообщений. XML проверен локальным XML-парсером и успешно запущен SIPp 3.7.7 на DID 74990000010; пользователь подтвердил эхо, итог 1 success/0 fail.

Для первого теста выбран 74990000010. Ожидается звонок на зарегистрированный 3400 либо 3401; ответить, проверить эхо голоса, завершить на выбранном клиенте. Сохранить итог SIPp и наблюдение сотрудника. Один Successful call сам по себе не доказывает, что сотрудник ответил: tp-entry заранее выполняет Answer, поэтому результат телефона и/или CLI нужен отдельно.

Журналы именуются sipp-inbound-DID-messages.log и sipp-inbound-DID-errors.log в /var/log/asterisk. Начальный INVITE содержит X-Lab-Trace: lab-DID-PID-CALL и X-Customer-ID: customer-001 для будущей проверки Queue. Перенос первых значений X-* подготовлен в copy-provider-headers через PJSIP_INHERITABLE_HEADER, применён и проверен для X-Lab-Trace/X-Customer-ID на операторе Queue; docs/headers.md и evidence/queue-headers.md. Предыдущий UAS уже завершился; одновременно два сценария на порту 5062 не запускаются.

Читать: [SIPp keywords](https://sipp.readthedocs.io/en/latest/scenarios/keywords.html), service, next_url, peer_tag_param и last_*; [XML scenarios](https://sipp.readthedocs.io/en/latest/scenarios/ownscenarios.html).
## Последовательная проверка остальных общих DID

scripts/test_general_dids.sh по умолчанию проверяет 74990000001–74990000009. Его нужно отдельно передать в /usr/local/sbin и запустить через sh. Зарегистрировать 3300, отвечать и завершать каждый вызов; остальные звонки в это время не выполнять. Программа запускает только один SIPp за раз, без полного SIP-логирования; временный verbose channel lab-did-range.log фиксирует маршруты. Выход SIPp и его экраны сохраняются по каждому DID, на консоль выводится короткий PASS/FAIL.

PASS требует кода завершения SIPp 0, точного Request-URI, увеличения числа вызовов Queue и увеличения числа ответов 3300 на lab-provider в текущем журнале. Сравниваются счётчики до/после каждого последовательного вызова. Журнал может содержать прошлые запуски; дельты не засчитывают старые ответы. При ошибке лог указывает экран SIPp для диагностики. Отдельный общий DID можно повторить аргументом скрипта. Синтаксис проверен bash -n; на VPS запуск завершился девятью PASS и итогом passed=9 failed=0. Все 11 DID с учётом 000/010 подтверждены; evidence/did-range.md.
Текущий итог диапазона: 11 из 11 DID проверены в лаборатории. Оставшиеся отрицательные случаи и распределение между несколькими операторами фиксируются в tests/acceptance.md, отдельно от проверки самого диапазона.

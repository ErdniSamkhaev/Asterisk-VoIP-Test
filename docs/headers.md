# Передача SIP-заголовков оператору КЦ

## Состояние

Перенос подготовлен в config/extensions.conf. Наличие PJSIP_INHERITABLE_HEADER на VPS подтверждено через core show function; модуль res_pjsip_header_funcs загружен. После инструкции заменить extensions.conf пользователь выполнил dialplan reload и получил Dialplan reloaded. Проверка двух SIP-плеч выполнена: X-Lab-Trace и X-Customer-ID совпали во входящем INVITE и INVITE к 3300. Queue и ответ оператора подтверждены тем же каналом; evidence/queue-headers.md.

## Политика переноса

Из входящего INVITE доверенного лабораторного провайдера копируется первое значение каждого заголовка с префиксом X-. Это согласованный для стенда набор служебных данных; стандартные Via, From, To, Call-ID, Contact, CSeq и прочие поля нового SIP-диалога формируются Asterisk. Прозрачное копирование всего входящего SIP-пакета не выполняется.

PJSIP_HEADERS возвращает уникальные имена; повторные экземпляры одного имени текущая реализация не переносит. Пустое первое значение допускается. Политика ограничена первым входящим INVITE; UPDATE, re-INVITE и заголовки ответов сюда не входят.

## Механизм

1. В from-provider для общего диапазона DID 74990000000–74990000009 вызывается Gosub(copy-provider-headers,s,1) до входа в IVR.
2. PJSIP_HEADERS(X-) получает имена из входящего INVITE исходного канала. SHIFT последовательно извлекает имя из рабочей переменной.
3. PJSIP_HEADER(read,имя,1) читает первое значение.
4. PJSIP_INHERITABLE_HEADER(add,имя) создаёт наследуемый заголовок на канале вызывающего.
5. Queue создаёт исходящий PJSIP-канал оператора и наследует channel datastore. Заголовок добавляется в его INVITE. При другой попытке распределения новый канал также получает подготовленные данные.

Функция доступна в ветке 22 начиная с 22.9.0; стенд использует 22.11.0. Собственное наследование переменных __ и pre-dial b() для этой реализации не требуются. На более ранних версиях понадобилась бы другая реализация, например переменные плюс обработчик b() с PJSIP_HEADER на канале вызываемого.

Прямой набор сотрудника из IVR также создаёт дочерний канал и наследует эти данные. Внутренний 2000 не проходит from-provider, поэтому заголовки внутренних клиентов эта подпрограмма не копирует. DID техподдержки 74990000010 идёт отдельной веткой и подпрограмму не вызывает: требование переноса проверяется именно на операторе очереди КЦ.

## Проверка

UAC-сценарий sipp/provider-uac.xml посылает X-Lab-Trace: lab-DID-PID-CALL и X-Customer-ID: customer-001. Для теста DID 74990000000 зарегистрировать 3300, включить SIP-логирование, выполнить входящий сценарий без DTMF и дождаться вызова из Queue. Ответить, проверить эхо, завершить и выключить SIP-логирование.

Сравнить два INVITE одного вызова: SIPp → Asterisk на DID и Asterisk → 3300. В обоих должны присутствовать одинаковые значения X-Lab-Trace и X-Customer-ID. Call-ID разных плеч может отличаться; сквозным идентификатором теста служит X-Lab-Trace. Одного наличия заголовков в исходном XML или на канале вызывающего недостаточно — нужен исходящий INVITE оператору из очереди.

Одиночный проверочный вызов уже выполнен: SIPp 1 success/0 fail, пользователь подтвердил эхо. Сравнение выполнено: оба тестовых X-* совпали, Queue и ответ 3300 подтверждены.

## Скрипт одного проверочного вызова

scripts/test_queue_headers.sh передать как /usr/local/sbin/test_queue_headers.sh и запускать через sh от root. Он создаёт временный файловый logger channel lab-headers.log уровня verbose, включает pjsip logger и запускает UAC на 74990000000. После завершения или INT/TERM выполняет cleanup: выключает pjsip logger и удаляет временный logger channel. Файл /var/log/asterisk/lab-headers.log сохраняется для проверки; при повторных запусках может дополняться. Сырые журналы не входят в репозиторий.

Держать 3300 зарегистрированным. После приветствия и 5-секундного ожидания вызывается Queue; ответить на 3300, проверить эхо, завершить на телефоне. В конце должны появиться сообщения об отключении PJSIP logging и удалении временного канала. Скрипт запущен на VPS: вызов успешен, эхо слышно; сообщения Logging disabled и Removed dynamic logger channel подтверждены. Пары заголовков прочитаны и совпали в двух INVITE; Queue подтверждён.

После теста извлечь INVITE на DID и INVITE на 3300 с X-Lab-Trace/X-Customer-ID, а также строку Queue из того же файла. Пример фильтра: grep -E 'INVITE sip:(74990000000@|3300@)|X-Lab-Trace:|X-Customer-ID:' /var/log/asterisk/lab-headers.log. При повторных тестах сопоставлять уникальный X-Lab-Trace, а не смешивать строки разных запусков.

Команды logger add/remove channel проверены по [исходникам logger.c 22.11.0](https://github.com/asterisk/asterisk/blob/22.11.0/main/logger.c#L1461).

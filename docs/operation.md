# Эксплуатация и диагностика

Документ описывает проверку итогового стенда и интерпретацию результатов. Инструкции выполняются на Linux-сервере с Asterisk; для доступа к состоянию служб и информации о процессах нужны соответствующие права.

## Проверка версии и управляющего подключения

```bash
asterisk -V
asterisk -rx "core show version"
```

Первая команда выводит версию исполняемого файла. Вторая подключается к работающему Asterisk через локальный управляющий Unix-сокет, выполняет команду CLI и возвращает результат в оболочку.

Ошибка Unable to connect to remote asterisk означает, что клиенту не удалось подключиться к управляющему сокету. Среди возможных причин — отсутствие работающего процесса, другой путь к сокету и ограничения доступа. По одному сообщению нельзя выбрать причину. Слово remote в этом сообщении относится к клиентской консоли Asterisk и само по себе не указывает на проблему с SIP-провайдером.

## Состояние службы и журнал

```bash
systemctl status asterisk.service --no-pager -l
journalctl -u asterisk.service -b -n 50 --no-pager
```

В systemctl смотреть:

- Loaded — найден ли механизм запуска и откуда он загружен.
- Active — состояние службы с точки зрения systemd.
- Последние сообщения — возможные причины остановки или неудачного запуска.

Встречающийся вариант Loaded: loaded (/etc/init.d/asterisk; generated) указывает на управление через сгенерированную обёртку для init-скрипта. При диагностике учитывать конкретный механизм запуска на сервере.

journalctl с параметром -u выбирает службу, -b ограничивает текущей загрузкой системы, -n 50 — последними 50 записями. Даты в журнале могут относиться к более раннему событию в пределах текущей загрузки. Не переносить состояние исторического процесса на текущий момент без проверки.

## Проверка фактических процессов и сетевых сокетов

```bash
pgrep -a -x asterisk
ss -lntup
```

pgrep с -x ищет точное имя процесса asterisk, -a выводит PID и полную командную строку. Пустой результат означает, что при проверке процессы с этим именем не найдены в доступной области просмотра процессов.

ss показывает TCP/UDP-сокеты: -l — слушающие и привязанные к локальному адресу UDP-сокеты в соответствующем представлении, -n — числовые адреса и порты, -t — TCP, -u — UDP, -p — связанные процессы. Для UDP нормален статус UNCONN. Для полного отображения владельцев процессов обычно требуются права root.

Найденный сетевой сокет не доказывает доступность из Интернета: её проверяют отдельно с учётом сетевых правил и маршрутов. Эта команда также не проверяет управляющий Unix-сокет Asterisk.

Если журнал содержит Unit process ... remains running after unit stopped, проверка процессов нужна до выбора следующего действия: состояние службы inactive не является достаточным доказательством отсутствия оставшегося процесса.

## Сообщения о RADIUS

Сообщение о невозможности открыть /etc/radiusclient-ng/radiusclient.conf фиксирует отсутствие или недоступность указанного файла в момент события. Его наличие в журнале не доказывает причину остановки всего Asterisk. Необходимость RADIUS-компонентов и настройки соответствующих модулей следует оценивать по конфигурации и требованиям стенда.

## Быстрая проверка итогового стенда

```bash
systemctl is-active asterisk.service tp-sync.timer
systemctl is-enabled asterisk.service tp-sync.timer
asterisk -rx "pjsip show contacts"
asterisk -rx "queue show cc"
asterisk -rx "database show tp"
journalctl -u tp-sync.service -n 15 --no-pager
```

Контакт Avail отвечает на qualify, Unavail — не отвечает; наличие контакта не равнозначно доступности клиента. Для телефона открыть SIP-клиент и повторно проверить доступность. Статический lab-provider NonQual ожидаем при qualify_frequency=0: для него регистрация не используется, а SIPp запускается только на время теста.

Таймер активен, а tp-sync.service после успешного oneshot может быть inactive. Снимок epoch|3401 указывает время и список; epoch| — успешное наблюдение без зарегистрированных ТП. Пустой список не является ошибкой скрипта. При сбое AMI скрипт не заменяет старую запись; dialplan отвергает её возраст свыше60секунд.

## Перезапуск без разговоров

```bash
asterisk -rx "core show channels count"
```

При0активных каналах выполнить перезапуск и проверить CLI после завершения загрузки модулей:

```bash
systemctl restart asterisk.service
asterisk -rx "core show version"
asterisk -rx "pjsip show contacts"
```

На стенде restart, восстановление доступности телефонов, повторные обновления AstDB, два провайдерских вызова Queue и последующий вызов ТП проверены. Autostart включён для АТС и таймера; reboot всего VPS не проверялся. При запуске наблюдалось сообщение stasis minimum_size/threadpool; его причина отдельно не разбиралась, успешные функциональные проверки приведены в evidence/restart-recovery.md.

## Заголовки и временная трасса

scripts/test_queue_headers.sh снимает один вызов, scripts/test_queue_headers_parallel.sh — два с разными данными. Оба используют trap для выключения pjsip logger и удаления динамического канала журнала. Во время захвата не выполнять посторонних звонков. Исходные трассы остаются в /var/log/asterisk и не публикуются.

```bash
grep -E 'INVITE sip:(74990000000@|330[01]@)|X-Lab-Trace:|X-Customer-ID:' /var/log/asterisk/lab-headers-parallel.log
```

Для ручного выключения незавершённой диагностики: asterisk -rx "pjsip set logger off". Динамический канал удалять по имени, использованному в конкретном тесте. Правила и ограничения передачи описаны в headers.md.

## Владельцы существующих рабочих данных

Только если выявлены файлы root, мешающие службе, и эти каталоги принадлежат данному стенду:

```bash
chown -R -h asterisk:asterisk /var/lib/asterisk /var/log/asterisk /var/spool/asterisk /var/cache/asterisk
```

Конфигурации, бинарные файлы и модули в этот список не включаются. Секреты root:asterisk640, каталог local750. Команды проверки не требуют публикации их содержимого.
